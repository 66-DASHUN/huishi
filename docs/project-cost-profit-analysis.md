# 绘世项目服务器承载、成本与盈利分析

生成日期：2026-06-17  
项目路径：`D:\AI\huishiv2`

## 1. 结论摘要

绘世当前是一个轻量级 AI 图像生成 Web 应用，后端为 Flask，数据库为 SQLite，图片默认保存在本地 `static/uploads`。从代码和运行日志看，服务器 CPU 与内存压力不大，真正决定业务吞吐的是生图上游 API 响应时间、后台生成线程数、SQLite 写入锁和图片存储/分发方式。

当前阿里云 `2核2G / 200M` 服务器适合内测和小规模商业化：

- 同时在线浏览用户：约 50-200 人。
- 普通页面/API 请求：约 20-80 QPS，取决于是否启用 Nginx/Gunicorn 和静态资源缓存。
- 同时生成任务：建议先限制在 3-5 个；当前 `.env.example` 推荐 10 个 workers，但 2G 内存下不建议一开始开满。
- 每日生成量：在单张生成约 60 秒、3-5 并发生成 workers 下，理论上限约 4,000-7,200 张/日；实际建议按 1,000-3,000 张/日规划，给失败重试、访问流量和上游波动留余量。

按你提供的真实成本：生图 API `0.05 元/张`。如果提示词优化每张都调用 DeepSeek，额外约 `0.002-0.006 元/次`。在现有套餐与积分规则下，1K/2K 每张收入约 `0.15-0.20 元`，4K 每张收入约 `0.30-0.40 元`。项目单张毛利较好，主要风险来自赠送积分、失败重试、支付手续费、服务器本地存储膨胀和上游 API 速度。

## 3. 服务器配置分析

### 3.1 已知配置

当前服务器：阿里云 `2核2G / 200M`。

这里的 `200M` 通常表示峰值带宽或套餐带宽上限。实际公网吞吐还取决于线路、地域、是否经 CDN、是否被平台限速、用户所在地和图片文件大小。

### 3.2 应用运行特点

该项目不是典型 CPU 密集型应用。一次生成请求的流程是：

1. 用户提交 `/generate`。
2. Flask 校验参数、校验积分、保存任务到 SQLite。
3. 后台线程调用上游生图 API。
4. 上游返回 base64 图片。
5. 应用解码并保存到本地。
6. 创建生成记录并扣积分。
7. 前端轮询任务状态并展示图片。

日志中实际样本显示，一次 2K 生图调用耗时约 `59.53 秒`。这说明用户等待时间主要来自上游 API，而不是本机计算。

### 3.3 关键瓶颈

#### 上游 API 耗时

如果单张图平均 60 秒，生成吞吐大致等于：

```text
每小时生成张数 = generation_workers * 3600 / 平均生成秒数
```

示例：

| workers | 平均 60 秒/张 | 理论每小时 | 理论每日 |
|---:|---:|---:|---:|
| 3 | 60 秒 | 180 张 | 4,320 张 |
| 5 | 60 秒 | 300 张 | 7,200 张 |
| 10 | 60 秒 | 600 张 | 14,400 张 |

这些是理想值，实际应打 40%-70% 折扣。

#### SQLite 写锁

SQLite 对低并发读写很合适，但高频写入时只有一个写事务能执行。项目中生成、扣积分、记录任务都会写数据库。当前设计适合小规模队列，不适合大量用户同时生成。

建议：

- 内测期：继续 SQLite。
- 日生成稳定超过 3,000 张，或同时生成任务超过 10 个：考虑迁移 PostgreSQL/MySQL。

#### Flask 开发服务器

日志显示当前使用的是 Flask development server，并提示不适合生产。正式上线必须使用：

- Nginx/Caddy 负责 HTTPS、静态资源、反向代理。
- Gunicorn/uWSGI/Waitress 等 WSGI server 运行 Flask。

如果继续使用 Flask development server，生产并发和稳定性都会受限。

#### 本地图片存储

现在图片默认保存在 `static/uploads`。这会带来几个问题：

- 图片越来越多，服务器磁盘会被吃满。
- 备份困难。
- 删除用户或清理记录后容易出现数据库记录与文件不一致。
- 多实例部署时无法共享文件。
- 图片下载会占用应用服务器带宽。

建议尽快迁移到 OSS/COS/R2/S3 这类对象存储。

#### 前端轮询

用户生成时前端会每隔几秒请求任务状态。假设每个生成用户 5 秒轮询一次：

```text
轮询 QPS = 同时等待生成用户数 / 5
```

例如 100 个用户同时等待生成，轮询约 20 QPS。对 2C2G 不算高，但会增加 SQLite 读压力和日志量。

## 4. 并发能力估算

### 4.1 推荐生产运行参数

2核2G 建议从保守配置开始：

```env
HUISHI_GENERATION_WORKERS=3
HUISHI_MAX_GENERATION_COUNT=4
HUISHI_MAX_REFERENCE_IMAGES=7
HUISHI_MAX_REFERENCE_IMAGE_BYTES=5242880
HUISHI_MAX_CONTENT_LENGTH=33554432
```

WSGI 建议：

- Gunicorn：`2 workers + 2 threads` 或 `2 workers + 4 threads`。
- Windows 可用 Waitress；Linux 上建议 Gunicorn。
- Nginx 开启静态资源缓存和 gzip/br。

### 4.2 同时在线用户

估算口径：在线用户不等于同时发请求。多数用户只是浏览、编辑提示词或等待结果。

| 场景 | 推荐承载 |
|---|---:|
| 同时在线浏览 | 50-200 人 |
| 同时活跃操作 | 20-80 人 |
| 同时等待生成 | 20-100 人 |
| 同时真实生成 | 3-5 个起步，压测后再增 |

### 4.3 请求并发

如果使用 Nginx + WSGI：

- 普通页面/API：20-80 QPS 较稳。
- 静态资源：由 Nginx 或 CDN 承载，200M 带宽足够早期使用。
- 大图下载：建议交给对象存储或 CDN，否则会挤占应用带宽。

### 4.4 生成并发

当前核心变量：

- `HUISHI_GENERATION_WORKERS` 控制后台同时生成任务数。
- `HUISHI_IMAGE_API_TIMEOUT` 默认 180 秒。
- 日志样本中 2K 生图约 60 秒。

推荐：

| 阶段 | workers | 适合情况 |
|---|---:|---|
| 内测 | 3 | 最稳，低内存风险 |
| 小规模商用 | 5 | 观察 CPU、内存、API 成功率后启用 |
| 高峰活动 | 8-10 | 仅在迁移对象存储、优化 WSGI、监控充分后启用 |

## 5. 成本模型

| 服务器 | 以当前阿里云 2C2G/200M 实际购买价为准 |

### 5.2 单张变量成本

不调用 prompt 优化：

```text
单张变量成本 = 0.05 元
```

每张都调用 prompt 优化：

```text
单张变量成本 = 0.05 + 0.002~0.006 = 0.052~0.056 元
```

存储摊销很低。若每张图片平均 2MB：

```text
1,000 张约 1.95GB
OSS 月存储成本约 0.23 元
```

真正需要关注的是图片外网流量。如果图片全部由服务器公网带宽直接分发，200M 带宽虽然峰值够用，但高并发下载会影响应用响应。用 OSS/CDN 后会更稳。

## 8. 上线前风险与优化建议

### 8.1 必做项

1. 不要使用 Flask development server 上线。
2. 使用 Nginx/Caddy + WSGI server。
3. 设置强 `HUISHI_SECRET_KEY`、`HUISHI_ADMIN_PASSWORD`、`HUISHI_ENCRYPTION_KEY`。
4. 清理重复套餐。
5. 限制 `HUISHI_GENERATION_WORKERS=3` 起步。
6. 设置单用户同时生成任务上限，避免单个用户占满队列。
7. 把生成图片迁移到 OSS/COS/R2。
8. 做数据库和上传文件定时备份。

### 8.2 建议项

1. 接入支付后增加订单表、支付流水表、回调幂等校验。
2. 增加失败重试成本统计，避免上游失败造成隐性亏损。
3. 增加管理后台的经营看板：收入、成本、生成张数、失败率、客单价、毛利。
4. 给 prompt 优化加频率限制，防止被当成免费 LLM 接口刷。
5. 图片下载走对象存储签名 URL 或 CDN。
6. 当日生成量超过 3,000 张时，评估 PostgreSQL/MySQL。
7. 当同时等待生成用户超过 100 时，评估 Redis 队列和 WebSocket/SSE。

## 9. 推荐阶段路线

### 阶段 1：内测

目标：验证转化、提示词体验、上游稳定性。

- 服务器保持 2C2G/200M。
- workers = 3。
- SQLite + 本地存储可暂时保留。
- 每日关注：生成成功率、平均耗时、失败原因、API 成本、用户留存。

### 阶段 2：小规模付费

目标：安全收款，控制成本。

- 上对象存储。
- 上正式 WSGI + Nginx。
- 清理套餐与计费规则。
- 增加订单/充值流水。
- 设置单用户并发生成上限。

### 阶段 3：规模增长

目标：提升吞吐与稳定性。

- 数据库迁移 PostgreSQL/MySQL。
- 队列迁移 Redis/RQ/Celery。
- 静态资源和图片走 CDN。
- 生成 worker 可横向扩展。
- 经营数据日报自动化。

## 10. 关键公式

### 生成吞吐

```text
每日理论生成量 = workers * 86400 / 平均生成秒数
```

### 单张毛利

```text
单张毛利 = 单张积分收入 - 生图 API 成本 - Prompt 成本 - 支付手续费摊销 - 存储/流量摊销
```

### 盈亏平衡张数

```text
盈亏平衡张数 = 月固定成本 / 平均单张毛利
```

### 存储容量

```text
月新增存储 GB = 月生成张数 * 平均图片 MB / 1024
```

## 12. 最终建议

当前配置可以支撑产品内测和初期付费验证。不要急着升级服务器，优先做四件事：

1. 生产部署方式从 Flask development server 改为 Nginx + WSGI。
2. 生成图片迁移对象存储。
3. 将 workers 控制在 3-5，并增加单用户并发限制。
4. 清理套餐并接入真实支付/充值流水。

在你当前 `0.05 元/张` 的生图成本下，商业模型是可行的。只要控制赠送积分和失败重试，当前价格体系有足够利润空间。
