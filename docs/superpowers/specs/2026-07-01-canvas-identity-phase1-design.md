# 画布身份打通第一阶段设计

**日期**: 2026-07-01  
**范围**: 第 1 阶段，仅处理画布与主站账号、权限、计费身份打通，不包含结果回流、资产分类改造、运行时一键启动。

---

## 1. 背景

当前项目已经完成以下基础集成能力：

- 主站存在独立 `/canvas` 页面
- 资产页可将素材导入画布
- 画布配置已并入主站后台配置中心
- 计费规则与套餐页已统一收口到主站后台

但当前 `/canvas` 仍然主要表现为“主站承载的独立画布页面”，画布本身尚未与主站用户身份、权限和计费身份形成真正统一的运行上下文。

这会带来几个问题：

- 画布无法可靠识别当前主站用户是谁
- 画布内的能力无法天然继承主站 `user/admin` 权限边界
- 后续要接入扣费、结果回流、运行控制时，缺少统一身份基础
- 如果继续直接叠加功能，容易演变为“两套松散耦合系统”

因此第一阶段需要先完成“身份打通”，为后续所有画布能力建立统一基础。

---

## 2. 目标

把画布从“独立 iframe/页面能力”升级为“受主站账号、权限、计费身份控制的画布工作区”。

第一阶段完成后应满足：

- 用户必须先登录主站，才能进入画布
- 画布能识别当前用户是谁、是什么角色
- 画布会话失效时不能继续进入编辑态
- 主站继续作为唯一身份源
- 后续所有扣费、结果回流、运行控制都可以基于统一身份继续扩展

---

## 3. 非目标

本阶段明确不做以下内容：

- 画布结果回流到主站资产库
- 资产库分类改为“全部 / 图片 / 画布”
- 主站对 canvas runtime / Agent/MCP 的真实一键启动
- 双向实时资产同步
- 画布独立用户表
- 双系统用户映射表

这些内容会在后续阶段单独设计与实施。

---

## 4. 架构原则

### 4.1 单一身份源

主站是唯一身份源。  
画布不维护独立账号体系，不自行登录，不创建独立用户记录。

### 4.2 画布只消费主站签发会话

主站为当前登录用户签发短时有效的 `canvas session token`。  
画布只信任来自主站的会话令牌，并据此建立当前用户运行上下文。

### 4.3 主站拥有最终权限与计费裁决权

画布只负责交互与编辑。  
凡是涉及权限、扣费、资产归属、审计的最终裁决，都必须回到主站完成。

### 4.4 渐进式集成

第一阶段只建立身份基础，不把结果回流、扣费执行、运行控制全部混进同一轮改造，避免系统边界失控。

---

## 5. 方案选型

已确认采用：

### 方案 A：主站签发会话，画布信任主站

实现方式：

- 用户在主站登录
- 用户从主站访问 `/canvas`
- 主站签发短时 `canvas session token`
- 画布启动后校验该 token
- 校验成功则建立当前用户上下文
- 校验失败则进入未授权态

选择原因：

- 最符合“统一账号、统一权限、统一计费身份”的目标
- 后续结果回流、扣费、运行控制都能继续复用
- 避免出现双用户系统或松散映射系统

不采用的方向：

- 纯 iframe 宿主转发模型：对后续能力扩展限制过大
- 双系统账号映射：复杂度高，当前阶段没有必要

---

## 6. 会话模型

### 6.1 Token 内容

主站签发的 `canvas session token` 至少包含以下信息：

- `user_id`
- `username`
- `role`
- `billing_identity`
- `expires_at`

说明：

- `billing_identity` 表示后续主站进行扣费判断所需的统一身份字段
- token 只携带画布运行所需最小信息，不包含不必要的敏感业务数据

### 6.2 Token 生命周期

采用短时有效 token，推荐有效期为 5 到 15 分钟。

理由：

- 降低被滥用风险
- 更适合 iframe / 嵌入式工作区场景
- 便于后续增加静默续签机制

### 6.3 续签策略

第一阶段允许先实现“短时 token + 失效后重新进入”。  
若当前代码结构允许，可预留静默续签接口边界，但不要求在本阶段完成复杂续签流。

---

## 7. 请求流设计

### 7.1 正常进入流程

1. 用户在主站登录
2. 用户访问 `/canvas`
3. 主站校验当前登录态
4. 主站为当前用户签发 `canvas session token`
5. 主站将 token 与必要上下文传给画布
6. 画布启动执行 `session bootstrap`
7. 画布校验 token
8. 校验成功后进入编辑态

### 7.2 失效流程

1. token 已过期、无效或缺失
2. 画布 bootstrap 失败
3. 画布不进入编辑态
4. 显示未授权 / 会话失效界面
5. 引导用户返回主站重新进入

### 7.3 未登录流程

1. 用户未登录主站
2. 用户直接访问 `/canvas`
3. 主站先拦截登录态
4. 未登录用户不能获得有效画布会话

---

## 8. 权限边界

### 8.1 角色来源

角色完全沿用主站当前角色体系：

- `user`
- `admin`

本阶段不新增画布专属角色。

### 8.2 普通用户能力

普通用户只能：

- 进入自己的画布工作区上下文
- 使用属于自己的素材与后续回流结果
- 触发属于自己的计费动作

### 8.3 管理员能力

管理员除普通能力外，还应允许使用主站侧诊断、配置和运行状态相关能力。

### 8.4 权限裁决位置

画布可以基于 token 渲染界面，但最终权限裁决仍应由主站接口完成。  
画布不应成为权限规则的唯一判断点。

---

## 9. 计费边界

### 9.1 核心原则

画布不直接做最终扣费。

### 9.2 执行方式

后续所有消耗型动作，应统一走主站计费接口，由主站判断：

- 当前用户是谁
- 当前角色是否允许执行
- 当前积分是否足够
- 当前动作应匹配哪条计费规则
- 是否需要记录审计

### 9.3 本阶段落点

第一阶段先定义并接通统一身份基础，不要求完整实现所有画布内扣费动作。  
但后续扣费接口必须以这一阶段的身份模型为前提继续扩展。

---

## 10. 主站职责

第一阶段主站需要新增或改造以下能力：

### 10.1 画布会话签发

主站为当前登录用户生成短时 `canvas session token`。

### 10.2 画布会话校验能力

主站需要提供以下两种方式之一：

- 会话校验接口
- 或明确的签名校验规则，供画布本地验证

优先建议：以主站可控的校验方式为准，避免画布侧自行推断主站会话真伪。

### 10.3 `/canvas` 页面上下文输出

主站在加载 `/canvas` 时，需要把当前用户的最小安全上下文传递给画布启动层。

### 10.4 后续统一计费入口预留

虽然本阶段不接完所有扣费动作，但主站需要保留画布动作未来走统一计费的接口边界。

---

## 11. 画布职责

第一阶段画布需要新增或改造以下能力：

### 11.1 Session Bootstrap

画布启动时优先完成以下步骤：

- 获取主站传入 token
- 校验 token
- 建立当前用户上下文
- 标记当前角色

### 11.2 未授权态

当 token 缺失、失效或校验失败时：

- 画布不能进入编辑态
- 显示明确的错误或失效提示
- 给出返回主站重新进入的指引

### 11.3 临时上下文缓存

画布可以在运行期持有短时上下文，但不应把它升级成独立账号体系或长期持久化用户身份。

---

## 12. 页面与交互表现

用户感知层面，第一阶段完成后应表现为：

- 用户仍从主站进入画布
- 画布仍保留当前独立工作区体验
- 但画布已识别当前主站用户身份
- 未授权或会话失效时会被阻止进入编辑态

这意味着：

- 画布不再只是“嵌在主站里的外部工具”
- 而是“主站当前用户的画布工作区”

---

## 13. 接口边界清单

### 13.1 主站接口

第一阶段至少需要以下边界：

- `canvas session 签发`
- `canvas session 校验`
- `canvas context 输出`

### 13.2 画布入口能力

第一阶段至少需要以下边界：

- `session bootstrap`
- `unauthorized state`
- `expired handling`

### 13.3 后续依赖边界

以下能力在后续阶段建立在当前阶段之上：

- 画布结果回流资产库
- 画布动作统一扣费
- 画布运行态控制
- 资产分类扩展

---

## 14. 实施范围控制

为了避免第一阶段膨胀，实施时必须控制以下边界：

- 不顺手引入双用户表
- 不在本阶段接全所有画布动作
- 不把运行时自动启动混入身份打通阶段
- 不把资产分类和结果回流强行并入同一轮

如果实现中出现对这些能力的依赖，应只留清晰接口边界，不应提前把整套功能实现进去。

---

## 15. 验收标准

第一阶段完成后，必须满足以下验收条件：

1. 用户必须先登录主站，才能进入画布
2. 画布可以识别当前主站用户身份
3. 画布可以识别当前主站角色
4. 未授权或过期会话不能进入画布编辑态
5. 主站仍是唯一身份源
6. 后续扣费、结果回流、运行控制已经具备统一身份基础

---

## 16. 后续阶段衔接

当第一阶段完成后，建议按如下顺序继续：

### 第二阶段

资产库分类扩展为：

- 全部
- 图片
- 画布

### 第三阶段

实现：

- 资产导入画布增强
- 画布结果回流主站资产库

### 第四阶段

实现：

- canvas runtime 检测
- Agent/MCP 检测
- 启动与状态控制

---

## 17. 设计结论

第一阶段采用“主站签发会话，画布信任主站”的方案，以最小闭环建立画布身份统一基础。

这一阶段的核心价值不在于立刻做出所有画布联动能力，而在于先把以下系统性问题一次性定住：

- 谁在使用画布
- 使用者属于什么角色
- 后续按谁计费
- 后续结果归谁
- 哪一侧拥有最终权限裁决

这一步打通后，后续资产回流、计费统一、运行控制都可以继续沿同一套边界推进，而不会再退回到“匿名 iframe + 临时拼接”的状态。
