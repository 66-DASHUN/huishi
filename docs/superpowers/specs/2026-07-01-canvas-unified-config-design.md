# 画布兼容接入与统一配置计费设计

> 目标：在不强行合并为单服务的前提下，把 `infinite-canvas` 兼容接入当前 `huishihuabu` 项目，并实现统一后台、统一配置、统一计费、统一资产入口与统一用户体验。

## 1. 设计结论

本阶段不做“技术上的单服务重构”，而是做“用户感知上的单系统整合”。

用户看到的是：

- 一个登录态
- 一个左侧导航
- 一个配置中心
- 一套积分与计费说明
- 一个资产库
- 一个画布入口
- 一套管理员权限

技术实现继续保留两个运行单元：

- `huishihuabu`：主系统，负责账号、权限、配置、积分、计费、资产、记录、后台
- `infinite-canvas`：画布运行时，负责画布编辑、节点交互、画布内工作流

这样做的原因：

- 能完整保留画布项目现有功能，避免为了合并运行时而削弱能力
- 不破坏当前 Flask 项目的稳定页面与业务逻辑
- 能优先完成真正重要的统一能力：配置、计费、资产、权限
- 为后续是否做“真单服务”保留演进空间

## 2. 架构原则

### 2.1 对用户统一

对外必须表现为一个系统：

- 统一入口
- 统一后台菜单
- 统一配置中心
- 统一计费规则
- 统一资产导入路径
- 统一用户权限

### 2.2 对技术保持边界

本阶段不把 `infinite-canvas` 的 React / Next.js 代码硬迁进 Flask 模板体系。

边界定义如下：

- 主系统负责业务规则和后台管理
- 画布服务负责画布交互和内部节点逻辑
- 两者通过明确的配置项和桥接协议协作

### 2.3 统一规则优先于统一运行时

本项目优先统一：

- 配置
- 计费
- 用户
- 权限
- 资产

暂不优先统一：

- 前端技术栈
- 运行时框架
- 画布内部状态管理实现

## 3. 页面规划

### 3.1 用户侧页面

保留并统一以下页面：

- `/workspace`：生成工作台
- `/canvas`：独立画布页
- `/assets`：资产库
- `/pricing`：计费说明
- `/account`：账号页

其中 `/canvas` 仍是独立页，但在导航、权限、配置、计费、资产导入方面属于主系统的一部分。

### 3.2 左侧导航

用户侧左侧导航统一为：

- 生成
- 画布
- 资产
- 计费说明
- 账号

要求：

- “画布”按钮位于“资产”之前
- 画布入口固定存在，不因是否在独立服务运行而改变导航结构

### 3.3 管理后台结构

后台统一为配置中心模式，采用“总页 + 左侧子导航 + 右侧内容区”的多页结构。

建议后台入口：

- `/admin/config`

建议子分区：

- `base`：基础配置
- `providers`：模型与 Provider 配置
- `canvas`：画布配置
- `agent`：Agent / MCP 配置
- `templates`：默认模板
- `billing`：计费规则
- `packages`：套餐说明
- `alerts`：告警与日志

兼容旧入口：

- `/settings` 保留可访问能力，但跳转或收口到统一配置中心
- `/admin/pricing` 收口到 `billing`
- `/admin/packages` 收口到 `packages`

## 4. 统一配置设计

### 4.1 配置存储原则

所有画布相关配置统一保存在当前主系统数据库中，由管理员在统一页面中维护。

已有可复用存储：

- `app_settings`

### 4.2 画布配置项

统一在“画布配置”分区管理：

- `canvas_app_url`：画布应用地址
- `canvas_agent_url`：Agent / MCP 地址
- `canvas_agent_token`：Agent Token
- `canvas_local_start_cmd`：本地启动参数
- `canvas_default_template`：默认模板

建议新增布尔类配置项：

- `canvas_enabled`：是否启用画布功能
- `canvas_asset_import_enabled`：是否允许从资产库导入
- `canvas_reference_import_enabled`：是否允许从参考图导入

### 4.3 配置生效逻辑

主系统负责：

- 从数据库读取画布配置
- 决定是否展示入口和空态提示
- 给画布页提供所需的运行配置

画布系统负责：

- 消费主系统传入的配置
- 在本地完成画布编辑逻辑

## 5. 统一计费设计

### 5.1 总原则

画布不单独创造一套新的计费体系。

统一使用当前主系统已有的积分规则：

- 按模式计费
- 按分辨率计费
- 由主系统进行积分扣减

### 5.2 规则来源

统一规则来源：

- `pricing_rules`

统一套餐说明来源：

- `packages`

### 5.3 管理方式

管理员在配置中心统一管理：

- 计费规则
- 套餐说明
- 计费展示文案

普通用户可见：

- 计费说明
- 套餐说明

普通用户不可修改：

- 计费规则
- 套餐配置

### 5.4 适用范围控制

建议在规则层支持适用范围控制，但仍保持一套规则源。

建议字段：

- `applies_to_workspace`
- `applies_to_canvas`

这样可以：

- 继续统一规则来源
- 同时允许特殊规则只在画布或工作台生效

如果当前阶段不扩字段，则默认画布与工作台完全共用现有规则。

## 6. 资产与画布联动

### 6.1 资产归属

资产继续统一由主系统管理，数据来源不分叉。

统一资产来源：

- 主系统生成图
- 用户收藏资产
- 用户上传参考图

### 6.2 画布导入入口

建议统一支持三种导入路径：

- 资产库中选中图片后“发送到画布”
- 工作台当前生成图“送入画布”
- 参考图直接导入画布

### 6.3 交互流程

主系统负责：

- 收集选中资产
- 组织桥接数据
- 发起跳转或消息桥接

画布负责：

- 接收桥接数据
- 自动插入图片节点
- 让用户继续编辑

### 6.4 桥接机制

本阶段允许继续使用现有的轻量桥接机制：

- `sessionStorage`
- `postMessage`

要求：

- 保持握手协议稳定
- 避免 iframe 加载时序导致丢图
- 保留完整画布端插入能力

## 7. 权限设计

### 7.1 管理员

管理员可：

- 查看配置中心全部分区
- 编辑画布配置
- 编辑 Agent / MCP 配置
- 编辑默认模板
- 编辑计费规则
- 编辑套餐说明

### 7.2 普通用户

普通用户可：

- 进入画布页
- 从资产导入画布
- 查看计费说明
- 使用与自身权限相符的画布生成能力

普通用户不可：

- 编辑后台配置
- 修改计费规则
- 修改套餐说明

## 8. 数据归属设计

### 8.1 继续统一在主系统的数据

以下数据必须继续由主系统持有：

- 用户
- 权限
- 配置
- 积分
- 计费规则
- 套餐说明
- 资产记录
- 生成记录

### 8.2 继续保留在画布侧的数据

以下数据允许继续在画布侧维护：

- 画布内部状态
- 节点布局
- 画布局部缓存
- 画布内部 UI 状态

## 9. 分阶段实施建议

### 阶段 1：统一后台入口

目标：

- 设置、计费、套餐、画布配置全部收口到统一配置中心

完成标准：

- 管理员只在一个后台入口里改配置

### 阶段 2：统一计费

目标：

- 画布生成明确走主系统积分校验和扣点逻辑

完成标准：

- 画布与工作台不存在两套并行计费口径

### 阶段 3：统一资产流转

目标：

- 资产库、工作台生成图、参考图全部可导入画布

完成标准：

- 用户可从主系统任意主要图片入口把素材送到画布

### 阶段 4：统一用户体验

目标：

- 整理导航、状态提示、空态、权限展示和错误提示

完成标准：

- 用户只感知一个产品，而不是两个站点拼接

## 10. 验收标准

设计落地后必须满足：

- 左侧导航包含独立画布入口
- 画布保持完整能力，不因接入主系统而弱化
- 管理员在统一后台中修改画布配置
- 计费规则只有一套来源
- 普通用户只看计费说明，不可修改规则
- 资产可直接送入画布
- 旧设置页和旧计费页保持兼容入口
- 当前阶段不依赖单服务重构

## 11. 风险与边界

### 11.1 不建议当前阶段做的事

不建议当前阶段：

- 强行把 `infinite-canvas` 全量迁成 Flask 模板
- 为画布单独再造一套计费体系
- 为画布单独再造一套后台
- 为了“单服务”提前做大规模前端架构迁移

### 11.2 当前设计的边界

本设计解决的是：

- 用户统一体验
- 后台统一管理
- 配置统一来源
- 计费统一来源
- 资产统一流转

本设计暂不解决的是：

- 真正意义上的单运行时
- 前端技术栈完全统一
- 画布代码仓与主项目代码仓彻底合并

## 12. 下一步

在本设计确认后，再单独编写实施计划，按以下顺序拆任务：

1. 配置中心整合
2. 计费规则收口
3. 资产到画布桥接完善
4. 页面入口与权限整理
5. 验收与回归测试
